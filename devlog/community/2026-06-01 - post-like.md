### 작업 2 — 동작 재확인 (`unlikePost` 로직)

5/31에 미리 짠 로직을 다시 정리:

**트랜잭션 흐름**
1. `BEGIN`
2. `assertPostExists` → post 미존재 시 404
3. `DELETE FROM post_likes WHERE post_id = $1 AND user_id = $2 RETURNING like_id`
4. `rowCount === 0` → 좋아요 안 누른 상태 → **400 `좋아요 내역이 없습니다.`** throw (명세서대로)
5. `UPDATE posts SET like_count = GREATEST(like_count - 1, 0) ... RETURNING like_count`
6. `COMMIT`

**`GREATEST(... - 1, 0)`의 의미**: 정상 흐름에서는 항상 1 이상에서 -1이 일어나므로 음수로 갈 일이 없지만, 동시 삭제 race나 다른 경로로 카운트가 어긋난 상태(예: 직접 SQL로 삭제했는데 카운트 미보정)에서 음수로 빠지는 것을 방지하는 안전망. 5/30 댓글 DELETE에서도 동일 패턴.

### 작업 3 — 로컬 테스트 6종 (DELETE + round-trip)

`npm run dev` nodemon이 라우트 추가에 자동 재기동된 직후 PowerShell로 호출. 응답 body의 `message`와 `data.like_count`까지 검증.

| # | 시나리오 | 기대 | 결과 |
|---|---|---|---|
| L7 | DELETE 비로그인 | 401 | ✅ |
| L8 | DELETE post=9999 (consumer) | 404 `해당 게시글을 찾을 수 없습니다.` | ✅ |
| L9 | DELETE post=18 (consumer 정상 취소) | 200, `like_count=1`, `좋아요 취소 완료` | ✅ |
| L10 | DELETE post=18 (consumer 중복 취소 — 이미 취소된 상태에서 또 시도) | **400 `좋아요 내역이 없습니다.`** | ✅ (DELETE RETURNING이 0행 반환 → 400 정상) |
| L11 | DELETE post=18 (brewery 정상 취소) | 200, `like_count=0` | ✅ |
| L12 | GET `/api/posts/18` — `like_count` 원복 | `like_count=0` | ✅ (5/31 시작 baseline으로 정확히 복귀) |

#### `like_count` 정합성 round-trip 종합

| 단계 | 동작 | `posts.like_count[18]` |
|---|---|---|
| 5/31 baseline | — | 0 |
| L3 | consumer POST | 1 |
| L4 | consumer 중복 POST → 400, 트랜잭션 ROLLBACK | 1 (변화 없음) |
| L5 | brewery POST | 2 |
| L9 | consumer DELETE | 1 |
| L10 | consumer 중복 DELETE → 400, 트랜잭션 ROLLBACK | 1 (변화 없음) |
| L11 | brewery DELETE | 0 |
| L12 종료 | — | **0 (baseline 복귀)** |

**핵심**: 실패 케이스(중복 등록/중복 취소)에서 트랜잭션 ROLLBACK이 정확히 동작해 카운트가 어긋나지 않았다. `post_likes` 행 수와 `posts.like_count`가 매 단계마다 일치.

### 세부사항

**DELETE 응답 status 200 vs 204**: 명세서 명시는 200. 일반 REST에서 본문 없는 DELETE는 204를 쓰기도 하지만 본 명세서는 `data: { post_id, like_count }`를 반환하므로 200이 맞다.

**중복 취소 케이스가 400인 이유**: 명세서 FAIL 1 "좋아요 내역 없음 (400) 좋아요 내역이 없습니다." 그대로. 사용자가 좋아요를 누르지 않은 상태에서 DELETE를 호출하면 클라이언트 측 상태(예: UI에 좋아요 활성 여부)와 서버 상태가 어긋났다는 신호이므로 200 idempotent 대신 400으로 알린다. 명세서 의도 그대로 따른다.

**테스트 후 RDS 정합**: post=18 좋아요 0개, `posts.like_count[18] = 0` — 5/31 시작 baseline과 동일. 다른 테스트 데이터는 13주차 댓글 작업에서 남은 `comment_id` 1·2·4(consumer 작성) 3개가 그대로 유지.
