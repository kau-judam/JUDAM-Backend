### 작업 1 — DailyToDo 12주차 계획 vs API 명세서 충돌점 검토

구현 시작 전, `01.CommonRules/DailyToDo/[커뮤니티]12주차 계획.md`와 `00.DefaultContext/API 문서/12주차/`의 3개 명세서를 대조했다. 5개 차이점을 발견했으며, **API 명세서가 프론트에 공개된 최신 문서이므로 충돌 시 항상 명세서를 기준으로 구현**한다는 원칙을 확인했다.

| 항목 | DailyToDo | API 명세서 | 처리 |
|---|---|---|---|
| GET 응답 필드 범위 | "포함 여부" 의문형 | 14개 필드 확정 | DB로 컬럼 존재 확인 후 명세서대로 |
| GET JOIN 대상 | POST_IMAGES만 명시 | + users·post_likes 필요 | DB 스키마 확인 후 명세서대로 |
| PUT 응답 형식 (vs GET) | — | GET=객체배열, PUT=문자열배열 | 의도된 설계 — 명세서대로 |
| PUT 요청 형식 | 단순 "수정" | multipart, 이미지 완전 교체, board_type 수정 불가 | 명세서대로 |
| DELETE cascade | 단순 삭제만 | POST_IMAGES/COMMENTS/POST_LIKES 함께 삭제 | DB에 `ON DELETE CASCADE` 이미 설정 — `DELETE FROM posts` 한 번으로 자동 처리 |

DB는 AWS RDS에 SSM 포트 포워딩으로 접속해 `posts`/`post_images`/`users`/`post_likes` 4개 테이블의 컬럼·FK 제약을 직접 확인했다.

### 작업 2 — `GET /api/posts/:postId` 게시글 상세 조회 구현

**이 API가 하는 일**: 특정 게시글 1개의 전체 상세 정보를 반환한다. 로그인하지 않아도 누구나 볼 수 있으며, 로그인한 경우 본인의 좋아요 여부와 본인 글 여부가 함께 반환된다.

**응답 구조** — 명세서 기준 14개 필드

```json
{
  "post": {
    "post_id": 17,
    "title": "...",
    "content": "...",
    "board_type": "INFO",
    "user_id": 2,
    "nickname": "테스트소비자",
    "author_profile_image": null,
    "like_count": 0,
    "comment_count": 0,
    "is_liked": false,
    "is_mine": true,
    "images": [
      { "sequence": 0, "image_url": "https://..." }
    ],
    "created_at": "2026-05-19T02:21:23.188Z",
    "updated_at": null
  }
}
```

**쿼리 구조**
- `posts JOIN users` — `nickname`, `author_profile_image` 획득
- `LEFT JOIN post_likes` — `is_liked` 판단 (비로그인 시 `user_id`가 null이라 자동 false)
- 별도 SELECT — `post_images`에서 `sequence` 오름차순으로 이미지 배열 조회

**비로그인 처리**: `optionalAuthMiddleware`로 토큰이 없으면 `req.user = null`이 되며, SQL의 `CASE WHEN p.user_id = $2`와 LEFT JOIN 조건의 `pl.user_id = $2`에 null이 들어가면 자연스럽게 false 반환. 코드에서 별도 분기 불필요.

### 작업 3 — `PUT /api/posts/:postId` 게시글 수정 구현

**이 API가 하는 일**: 작성자 본인만 자신의 게시글 제목·본문·이미지를 수정한다.

**요청 형식**: `multipart/form-data`
- `title` (필수)
- `content` (필수)
- `images[]` (선택, 최대 5개, **기존 이미지를 완전 교체**)

**이미지 완전 교체 흐름** (트랜잭션)
1. `posts.user_id` 조회 → 미존재 시 404, JWT의 user_id와 다르면 403
2. `UPDATE posts SET title, content, updated_at = CURRENT_TIMESTAMP`
3. `DELETE FROM post_images WHERE post_id = ?`
4. 새 이미지 파일을 S3 업로드 후 받은 URL을 `INSERT INTO post_images (post_id, image_url, sequence)`로 sequence 0,1,2... 순서로 재삽입
5. 이미지를 아예 전송하지 않으면 기존 이미지 전체 삭제(빈 목록으로 교체)

**`board_type`은 수정 불가** — 요청에 포함되어도 무시 (게시판 이동 금지).

**응답 형식**: 명세서대로 GET과 다른 축약 형식

```json
{
  "status": 200,
  "message": "게시글이 수정되었습니다.",
  "post": {
    "post_id": 17,
    "title": "...",
    "content": "...",
    "image_urls": ["https://..."],
    "updated_at": "2026-05-22T..."
  }
}
```

> GET 응답의 `images` 필드는 객체 배열, PUT 응답의 `image_urls`는 문자열 배열로 명세서에서 다르게 정의되어 있다. 프론트와 합의된 설계이므로 명세서대로 그대로 구현.

### 작업 4 — `DELETE /api/posts/:postId` 게시글 삭제 구현

**이 API가 하는 일**: 작성자 본인만 자신의 게시글을 삭제한다.

**삭제 흐름**
1. `posts.user_id` 조회 → 미존재 시 404, JWT의 user_id와 다르면 403
2. `DELETE FROM posts WHERE post_id = ?` 한 번 실행
3. FK `ON DELETE CASCADE`로 `post_images`, `post_comments`, `post_likes`가 자동 삭제

**응답**

```json
{
  "status": 200,
  "message": "게시글이 삭제되었습니다."
}
```

### 세부사항

**한글 인코딩 테스트 이슈**: PowerShell 환경의 `curl -F`로 multipart 요청을 보내면 한글이 CP949로 인코딩되어 깨진 채 DB에 저장된다. 백엔드 코드 문제는 아니며(GET 응답에서 기존 UTF-8 한글 데이터는 정상 반환됨), Thunder Client·프론트엔드 fetch 환경에서는 정상 동작한다. 테스트 중 깨뜨린 post_id=17의 원본 데이터는 아래 SQL로 사용자가 DBeaver에서 직접 복구해야 한다.

```sql
UPDATE posts
SET title = '[5.17]실제 서버 테스트',
    content = '게시글 타입 변경 이후 실제 서버에서 테스트.(이미지 포함)',
    updated_at = NULL
WHERE post_id = 17;

INSERT INTO post_images (post_id, image_url, sequence)
VALUES (17, 'https://judam-storage.s3.ap-northeast-2.amazonaws.com/uploads/2/1779189683082-123.png', 0);
```

**S3 정리**: PUT/DELETE 시 DB의 `post_images` 레코드는 정리하지만, **S3 객체 자체는 삭제하지 않는다**. 명세서에 S3 정리 요구가 없고 기존 POST 작성 API도 S3 정리 로직이 없는 일관성을 따랐다. 향후 스토리지 비용 누적이 문제가 되면 S3 객체 삭제 로직을 별도로 추가해야 한다.
