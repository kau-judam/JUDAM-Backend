### 작업 0 — 브랜치 생성 + 사전 환경 점검

13주차 두 번째 작업(WBS #14 게시글 좋아요)으로 진입. 어제(5/30) 댓글 CRUD 브랜치를 마감했고 좋아요는 별개 리소스(`/api/posts/{postId}/likes`)라 신규 브랜치 `feature/post-like`로 분기. dev를 최신화한 뒤 분기했고 충돌은 없다.

작업 시작 직후 SSM 포트 포워딩(`localhost:5433` → `judam-db` RDS)으로 운영 DB에 직접 붙어 `\d post_likes`로 테이블 구조를 검증:

| 컬럼/제약 | 명세서 메모 | 실제 RDS | 일치 |
|---|---|---|---|
| `like_id BIGSERIAL PRIMARY KEY` | 명시됨 | `nextval('post_likes_like_id_seq')` | ✅ |
| `post_id BIGINT NOT NULL` | FK→posts | `fk_post_likes_post` ON DELETE CASCADE | ✅ |
| `user_id BIGINT NOT NULL` | FK→users | `fk_post_likes_user` ON DELETE CASCADE | ✅ |
| `created_at TIMESTAMP` | 명시됨 | `NOT NULL DEFAULT CURRENT_TIMESTAMP` | ✅ |
| UNIQUE (post_id, user_id) | 명시됨 | `uq_post_likes UNIQUE` | ✅ (제약 이름은 schema.sql의 `uq_post_likes_post_user`와 다르지만 `23505` SQLSTATE 처리는 이름 무관) |

**마이그레이션 작성 불필요** — 이미 운영 RDS에 전체 컬럼·제약 완비. DDL 작업은 스킵.

작업 시작 전 baseline: `posts.like_count[18] = 0`, `post_likes`에 post=18 관련 행 0개. 깨끗한 상태에서 시작.

### 작업 1 — 명세서 vs DailyToDo 충돌 검토

| 항목 | DailyToDo | API 명세서 | 결정 |
|---|---|---|---|
| 성공 HTTP status | 명시 없음 | **200 OK** (201 아님) | 명세서대로 200 |
| 응답 키 이름 | 명시 없음 | `data: { post_id, like_count }` (`comment` 아님) | 명세서대로 `data` |
| 중복 좋아요 status | 명시 없음 | **400 Bad Request** (409 아님) | 명세서대로 400 |
| 권한 검증 | 명시 없음 | 본인 글에도 가능, 누구나 가능 | 권한 검증 없음 (403 케이스 없음) |
| 트랜잭션 범위 | "POSTS.like_count 자동 증가" | 명시 없음 | `post_likes INSERT` + `posts.like_count + 1` 두 쿼리라 트랜잭션 |

명세서 우선 원칙을 그대로 적용. 5/30의 mismatch 회귀 경험을 떠올리며, 명세서 공백을 임의 해석하지 않도록 주의.

### 작업 2 — `POST /api/posts/:postId/likes` 좋아요 등록 구현

**이 API가 하는 일**: 로그인한 사용자가 특정 게시글에 좋아요를 등록한다. 같은 사용자가 같은 게시글에 중복 좋아요를 누르면 DB UNIQUE 제약이 막아 400을 돌려준다. 등록 성공 시 `posts.like_count`가 +1 된다.

**트랜잭션 흐름** (`postLikeService.likePost`)
1. `BEGIN`
2. `assertPostExists` — `SELECT 1 FROM posts WHERE post_id = $1` → 미존재 시 404 throw
3. `INSERT INTO post_likes (post_id, user_id) VALUES ($1, $2)` — UNIQUE 위반 시 `e.code === '23505'` catch → 400 `이미 좋아요한 게시글입니다.` throw
4. `UPDATE posts SET like_count = like_count + 1 ... RETURNING like_count`
5. `COMMIT`

**응답** (명세서대로 200)
```json
{
  "status": 200,
  "message": "좋아요 등록 완료",
  "data": { "post_id": 18, "like_count": 1 }
}
```

**왜 `RETURNING like_count`로 직접 받는가**: 별도 `SELECT`를 한 번 더 안 쳐도 갱신된 값을 즉시 받을 수 있어 race 안전 (다른 트랜잭션의 +1과 섞이지 않음). PostgreSQL의 표준 패턴.

### 작업 3 — 라우트 등록

`src/routes/postRoutes.js`에 댓글 라우트 아래로 1줄 추가 (DELETE 라우트는 6/1에 추가 예정 — 같은 require 블록 안에 미리 import만 해두면 자연스러움).

```js
const { postLike, deleteLike } = require('../controllers/postLikeController');

// 좋아요 등록 — 로그인 필수 (UNIQUE 위반 시 400)
router.post('/:postId/likes', authMiddleware, postLike);
```

DELETE는 내일(6/1) 라우트 한 줄만 추가하면 되도록 controller의 `deleteLike`도 같이 export·import만 준비. 6/1 작업 분량을 명확히 분리하기 위해 5/31에는 라우트 라인을 등록하지 않는다.

### 작업 4 — 로컬 테스트 6종 (POST 전용)

`npm run dev` nodemon 재기동 후 PowerShell `Invoke-WebRequest` + UTF-8 바이트 직접 전송으로 호출. 응답 body의 `message`와 `data.like_count`까지 검증.

| # | 시나리오 | 기대 | 결과 |
|---|---|---|---|
| L1 | POST 비로그인 | 401 | ✅ |
| L2 | POST post=9999 (consumer) | 404 `해당 게시글을 찾을 수 없습니다.` | ✅ |
| L3 | POST post=18 (consumer 첫 좋아요) | 200, `like_count=1`, `좋아요 등록 완료` | ✅ |
| L4 | POST post=18 (consumer 중복) | **400 `이미 좋아요한 게시글입니다.`** | ✅ (UNIQUE `uq_post_likes` 위반 정상 catch) |
| L5 | POST post=18 (brewery 다른 사용자) | 200, `like_count=2` | ✅ (누적 카운트 정확) |
| L6 | GET `/api/posts/18` — `like_count` 누적 | `like_count=2` | ✅ |

**중복 좋아요 차단**: DB 레벨 UNIQUE 제약으로 차단 + 애플리케이션 레벨 `23505` SQLSTATE 매칭으로 의도된 400 반환. race condition에서도 DB가 직접 막아 안전.

5/31 시점에는 POST만 구현·테스트 완료. 6/1에 DELETE 추가 + 전체 round-trip 검증 예정. 따라서 RDS는 현재 post=18에 `(post_id=18, user_id=2)`, `(post_id=18, user_id=3)` 두 좋아요 행이 남아있고 `posts.like_count[18] = 2` 상태. 6/1 첫 작업에서 이 데이터를 그대로 활용해 DELETE 테스트.

### 세부사항

**왜 unlikePost / deleteLike까지 5/31에 미리 작성했나**: 두 함수는 동일 service/controller 파일에 묶는 게 자연스럽고, 라우트만 6/1에 등록하면 5/31 시점의 코드 동작에는 영향이 없다(노출되지 않은 endpoint). 6/1 작업이 "라우트 1줄 + 테스트 + devlog"로 깔끔히 떨어지도록 의도. 만약 5/31 PR을 단독으로 머지해야 한다면 controller의 `deleteLike` export와 routes의 import는 일시 제거 가능하지만, 13주차 5/29~5/30 패턴대로 같은 브랜치에 묶일 예정이라 그대로 유지.

**제약 이름 불일치 메모**: RDS는 `uq_post_likes`, schema.sql은 `uq_post_likes_post_user`. 향후 다른 환경에 schema.sql 그대로 적용하면 제약 이름이 다른 두 환경이 만들어진다. 코드는 SQLSTATE(`23505`)로 판별하므로 영향 없지만, 추후 schema.sql과 RDS를 한 쪽으로 통일하는 정리가 필요할 수 있다(별도 협의 사항 — 13주차 좋아요 작업의 범위 밖).
